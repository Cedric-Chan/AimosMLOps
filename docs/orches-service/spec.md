# Orches Service — Evals 与责任层产品规格（v1）

> 状态：v0.9 草案（2026-09-22）。本文是 2026-09-22 Evals Context 设计对齐会的产物，责任层五件套与评测集成在这里作为第一版产品定义。
> 证据与业界依据见 `docs/platform/research/_internal/Evals-Context-设计与业界借鉴.md`（内部，不入库）；术语见仓库根 `CONTEXT.md`。

## 1. 范围与定位

- **范围**：Orches Service 的评测闭环（评测集 → 失败转用例 → 版本回归 → 在线采样评分）与责任层（权限 / 审计 / 回滚 / 降级 / 归属）。
- **首期场景**（三场景同一套机制，2026-11 功能上线）：PH KYC 身份核验、TH 贷款材料目的核验、MY 名单类核验（具体服务名映射见内部调研文档与标准模板）。
- **路线**：Orches 原生自建，不引入 MLflow GenAI 运行时依赖（见 ADR-0001）。评测是离线负载：数据落在 regional 数仓与对象存储，平台只集中聚合指标层（见 ADR-0002 与决策 D3）。

## 2. 评测资产

| 资产 | 产品语义 |
|---|---|
| 评测集（Dataset） | 一个场景的「测试数据库」。归属平台（owner = 平台团队），业务团队只读 + 提交用例。用例 id 稳定、跨运行可 join。 |
| 用例（Dataset Item） | 一条可重复判定的输入 + 期望输出。可来自生产 trace 回灌、历史单据回灌、手工构造（无 trace）。入库按 input 去重；带来源标记与状态（draft / active / holdout / retired）。 |
| 评测运行（Eval Run） | 对某评测集的一次执行，记录「评测集版本 × 被测服务版本 × 评分器版本」三元组，保证可复现、可对比。 |
| 单例结果（Run Case） | 一次运行中每条用例的得分（scores）、输出、错误、trace 链接。trace_id 可空外键——手工用例没有 trace。 |

## 3. 关键用户旅程

### 3.1 失败 → 用例
生产侧在追踪日志（TracingLog）多选失败请求 → 「存为用例」→ 进入待审（人工闸门，**不自动采纳**）→ 平台评审后转入评测集。业务方在现有流程中的每一次**驳回/认可**自动回流为标注与候选用例（业务方零额外动作）。

### 3.2 版本发布门禁
- **11 月 v1（报告模式）**：确定性断言（JSON schema / 枚举 / 字段抽取 / 正则）阻塞发布；LLM judge 结果只进报告。
- **校准后（≥90% 一致率）**：已校准的 judge 升级为阻塞分支；未校准或跌破线的 judge 自动降回只报告。
- 强制点在服务端发布端点；前端仅做展示。

### 3.3 Judge 健康度（元指标）
每个场景一张健康度卡：judge 与人工标注在**同名反馈**上的一致率趋势、上次校准时间、是否具备阻塞资格。人工投入三个有界通道：分歧复核（最高价值）、定期校准批（30–50 条，事件触发：改 prompt / 换模型 / 一致率跌破线）、业务驳回回流。

## 4. 责任层（写进产品定义，不是上线前清单）

### 4.1 权限
对齐 Model Experiment 的四角色矩阵（Admin / TeamOwner / Member / Viewer）：

| 操作 | 最低角色 |
|---|---|
| 查看评测报告 | Viewer |
| 写评测集 / 标注 / 跑评测 | Member |
| **移动 production 指针（发布权）** | **TeamOwner 及以上** |
| 修改通过标准 / 删除评测集 | Admin |

### 4.2 审计
`promote`（指针迁移）与 `setLabel` 是**独立一等审计事件**，不淹没在 update 里。最小五元组：actor + actor_type（人 / API key）+ action + resource + timestamp，附 outcome。

### 4.3 回滚
回滚 = 「把 production 指回上一个通过门禁的版本」这一个动作。指针可变、版本对象不可变；不设计状态枚举。

### 4.4 降级
**产品定义：任何时刻的质量指标必须可归因——包括降级期间。** 每次调用记录「请求的模型」与「实际服务的模型」；质量看板上降级率与质量曲线并列。工程以一次降级演练验收此要求；验收不通过则降级率改由网关侧日志出具。

### 4.5 归属
`release`（应用整体版本，git SHA）随 trace 根落库，`component version`（节点级版本）挂节点。事故归因路径：trace 变差 → 某次变更让某组件变差。审计按变更记，报告按 release / component / dataset-version 聚合，**不按人聚合**。

## 5. 经营指标

平台团队背两个产出所有权指标：

| 指标 | 口径 |
|---|---|
| **评测覆盖率** | 有评测集覆盖的在跑 LLM 服务 ÷ 全部在跑 LLM 服务（分母来自节点日志，分子来自评测集） |
| **回归拦截数** | 门禁拦下的带病发布次数 |

业务结果（KYC 判定准确率、解析准确率等）：平台提供测量能力（口径 + 趋势），**达标由业务方负责**，不进平台 OKR。

## 6. 业务方参与（每场景三交付物）

1. **用例**：历史单据回灌首批 ≥50 条（正常 + 边界 + 已知失败模式），经平台脱敏与去重入库；持续通过驳回回流 + 采样补充。
2. **通过标准**：业务判据（审核标准 / 抽取标准 / 最终结论对错定义）由业务方填写并签署——业务不定准确率目标；工程判据（准确率 / 成本 / 延迟）由平台在成本约束下校准。模板见 `docs/orches-service/_internal/standards/`。
3. **签署人**：每场景一个具名业务 owner + 平台 PM（口径签署）。

## 7. 里程碑

| 时点 | 交付 |
|---|---|
| **2026-10**（赶 TH/MY 上线） | 三份《通过标准》签署（TH Nano / MY 2WL / PH）；签署人落定 |
| **2026-11** | 评测功能 v1：评测资产四表、失败转用例、PH 历史回灌、TH/MY 用例集首版、确定性门禁（报告模式）、judge 只报告 |
| **2026-12 起** | judge 校准实验（PH 先行）→ 达标后阻塞升级；在线采样评分按预算逐步开 |

## 8. 待确认项（工程）

1. 后端角色校验现状：四角色矩阵在后端发布端点是否已实现同等粒度（列入与后端团队排期沟通）。
2. 降级路径能否把「实际服务的模型」回吐到节点日志（一次演练验收，见 4.4）。
3. LLM 节点日志的 token / usage 字段现状（影响成本口径，已在节点日志参考文档中确认缺失，需运行时验证补齐方式）。
4. 评测集的 media 字段位随建表预留（二期图像评测用）。
