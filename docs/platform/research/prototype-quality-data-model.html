AI 质量数据模型 · 设计原型

「MLflow 的 Trace / Assessment / EvaluationDataset 三层模型——以『一次请求的完整执行（Trace）』为唯一锚点，机器评分、人工标注、业务反馈、问题发现全部落成同构的 Assessment 挂回 trace，评测集则是这些 trace 的『测试数据库』——能否表达 Aimos 的真实质量场景，并让『人 vs judge 对齐』『反馈回流成评测集』『门禁卡发布』在结构上自然成立？」

待确认的设计点

  1. 期望值只能人写。机器能给判定，不能给真值（LLM 写期望值一律被拒）。那真实场景里谁来写、写多少？这会不会成为评测集的产能瓶颈？
  2. 对齐必须先同名。「人 vs judge」的一致率只统计名称完全相同的反馈；不同名的人工标注只是独立信号。judge 名与标签规范由谁维护、怎么定？
  3. 评测集按 inputs 去重。同一 inputs 不重复入集（细微差异才算不同记录）。业务上能否接受「同一个案例只能有一条记录」？
  4. 评测集记录可以没有 trace。手工/合成样本的 traceId 为 null——这是「一切挂 trace」在这层的结构例外。要不要放开？还是坚持手工样本也必须先造 trace？
  5. 门禁是二分布尔。任何一行、任一 scorer 不过 = 整体失败；叠加非确定性 judge 会假失败。要不要用确定性 scorer 兜底、或改成 k-of-n / 多次取多数？
  6. 版本语义靠 tags。OSS 无数据集版本 API（version 静默返回 None），版本只能用 tags + versionNote 表达。够用吗，还是要自建版本表？
